# 21.01 Organisation du code et conventions

## Organisation du code

Le code est hors de `docs/`. Organisation prévue par la story `socle-1` :

| **Dossier** | **Contenu**                                                       |
| ----------- | ----------------------------------------------------------------- |
| `backend/`  | API Laravel 11+ (PHP 8.3+), routes `/api/v1/`, Sanctum            |
| `frontend/` | SPA Vue 3 + Vite + Pinia + vue-i18n                               |
| `docker/`   | Fichiers Docker Compose et configuration des services (`socle-2`) |

Les tests automatisés vivent avec le code : `backend/tests/` et `frontend/tests/`.

## Cycle d'une story

1. Choisir la prochaine story du sprint : `story-lifecycle implement <id>`.
2. Créer la branche de la fonctionnalité depuis `main` à jour : `git switch -c feature/<id>` (ex. `feature/socle-1`).
3. Vérifier les ADR dont elle dépend ([[13.00 Index des ADR]]).
4. Écrire les tests d'abord, puis le code ; commits sur la branche.
5. Publier la branche sur GitHub : `git push -u origin feature/<id>`.
6. Revue de code et boucle de vérification sur la branche ; tous les tests passent.
7. Intégrer à `main` par fusion sans avance rapide (`git merge --no-ff feature/<id>`), pousser `main`, puis supprimer la branche (locale et distante).
8. Passer la story à `done` via `ledger.js`, sur `main`.

## Branches

| **Branche**         | **Usage**                                                                                          |
| ------------------- | -------------------------------------------------------------------------------------------------- |
| `main`              | Branche d'intégration, toujours stable ; aucun commit de code direct.                              |
| `feature/<id>`      | Une fonctionnalité = une story (`<id>` = identifiant de la story, ex. `feature/identite-2`).        |
| `fix/<id>`          | Correction d'un bug suivi dans une fiche `52.xx` ou une story (ex. `fix/52.03`).                    |

- Une branche ne porte qu'une seule story ; elle part de `main` à jour et y revient par fusion `--no-ff`, pour garder la trace de la fonctionnalité dans l'historique.
- Si `main` a avancé, la branche est mise à jour (`git merge main`) et retestée avant intégration.
- Restent directement sur `main` : la documentation (`docs/`), le suivi (`.stories/` via `ledger.js`), les notes de session et plans (`.claude/`), et les commits de version ([[41.01 Versionnage et procédure de livraison]]).

## Conventions

- Langue de travail : français (documentation, commits, stories).
- Commits en français ; le code est commité sur sa branche de fonctionnalité, jamais directement sur `main` (voir « Branches »).
- Toute écriture dans `.stories/` passe par `ledger.js` du skill `story-lifecycle`.
- Les documents sont cités par leur identifiant Johnny.Decimal (voir [[00.00 Index]]).
- Le chiffrement des preuves se fait uniquement dans le navigateur : aucun code serveur ne manipule de clair.
- Les modèles Eloquent et les migrations partent de [[14.01 Schéma des objets métier]]. Avant la première migration métier, ce schéma est détaillé dans une nouvelle version (attributs, tables de liaison, liens polymorphes) et ses points « À préciser » sont tranchés.
