# 21.01 Organisation du code et conventions

## Organisation du code

Le code est hors de `docs/`. Organisation prévue par la story `socle-1` :

| **Dossier** | **Contenu**                                                       |
| ----------- | ----------------------------------------------------------------- |
| `backend/`  | API Laravel 11+ (PHP 8.3+), routes `/api/v1/`, Sanctum            |
| `frontend/` | SPA Vue 3 + Vite + Pinia + vue-i18n                               |
| `docker/`   | Fichiers Docker Compose et configuration des services (`socle-2`) |

Les tests automatisés vivent avec le code : `backend/tests/` et `frontend/tests/`.

## Cycle d'une story

1. Choisir la prochaine story du sprint : `story-lifecycle implement <id>`.
2. Créer la branche de la fonctionnalité depuis `main` à jour : `git switch --create feature/<id>` (ex. `feature/socle-1`).
3. Vérifier les ADR dont elle dépend ([[13.00 Index des ADR]]).
4. Écrire les tests d'abord, puis le code ; commits sur la branche.
5. Publier la branche sur GitHub : `git push --set-upstream origin feature/<id>`.
6. Revue de code et boucle de vérification sur la branche ; tous les tests passent.
7. Intégrer à `main` par fusion sans avance rapide (`git merge --no-ff feature/<id>`), pousser `main`, puis supprimer la branche (`git branch --delete feature/<id>` et `git push origin --delete feature/<id>`).
8. Passer la story à `done` via `ledger.js`, sur `main`.

## Branches

| **Branche**         | **Usage**                                                                                          |
| ------------------- | -------------------------------------------------------------------------------------------------- |
| `main`              | Branche d'intégration, toujours stable ; aucun commit de code direct.                              |
| `feature/<id>`      | Une fonctionnalité = une story (`<id>` = identifiant de la story, ex. `feature/identite-2`).        |
| `fix/<id>`          | Correction d'un bug suivi dans une fiche `52.xx` ou une story (ex. `fix/52.03`).                    |

- Une branche ne porte qu'une seule story ; elle part de `main` à jour et y revient par fusion `--no-ff`, pour garder la trace de la fonctionnalité dans l'historique.
- Si `main` a avancé, la branche est mise à jour (`git merge main`) et retestée avant intégration.
- Restent directement sur `main` : la documentation (`docs/`), le suivi (`.stories/` via `ledger.js`), les notes de session et plans (`.claude/`), et les commits de version ([[41.01 Versionnage et procédure de livraison]]).

## Conventions

- Langue de travail : français (documentation, commits, stories).
- Commits en français ; le code est commité sur sa branche de fonctionnalité, jamais directement sur `main` (voir « Branches »).
- Toute écriture dans `.stories/` passe par `ledger.js` du skill `story-lifecycle`.
- Les documents sont cités par leur identifiant Johnny.Decimal (voir [[00.00 Index]]).
- Le chiffrement des preuves se fait uniquement dans le navigateur : aucun code serveur ne manipule de clair.
- Les modèles Eloquent et les migrations partent de [[14.01 Schéma des objets métier]]. Avant la première migration métier, ce schéma est détaillé dans une nouvelle version (attributs, tables de liaison, liens polymorphes) et ses points « À préciser » sont tranchés.

## Style du code

Règles valables pour tout le code (PHP, TypeScript, Vue, JSON, YAML, scripts) ; les linters de la CI les rendent bloquantes (story socle-3).

### Indentation

- Indentation par **tabulations**, jamais par espaces ; l'alignement à l'intérieur d'une ligne n'utilise pas de tabulation.
- Le fichier `.editorconfig` à la racine fixe la règle pour les éditeurs (`indent_style = tab`, fins de ligne LF, encodage UTF-8, saut de ligne final).
- Exceptions imposées par le format : YAML (espaces obligatoires) et Markdown (listes et blocs de code de la documentation Obsidian).
- PHP : PHP-CS-Fixer (règles PSR-12, sauf l'indentation, remplacée par des tabulations). TypeScript et Vue : ESLint avec les règles de style `@stylistic` (`indent: tab`, `vue/html-indent: tab`).

### Commentaires

Le code est **bien commenté**, en français :

- chaque fichier, classe, composant Vue, store et fonction exportée a un commentaire d'en-tête (PHPDoc ou JSDoc) qui dit **à quoi il sert** et, si besoin, **quelle décision il applique** (identifiant de l'ADR ou de la partie du CDC, par exemple `13.04`) ;
- les paramètres, les valeurs de retour et les exceptions non évidents sont décrits (`@param`, `@returns`, `@throws`) ;
- à l'intérieur des fonctions, un commentaire explique le **pourquoi** d'un choix non évident (sécurité, contournement, contrainte d'un format), pas ce que le code dit déjà ;
- les tests portent un nom ou un commentaire qui énonce le comportement attendu, en français ;
- un commentaire faux est un défaut : il est corrigé dans le même commit que le code qu'il décrit.

### Paramètres des commandes

Dans les scripts, la CI, les fichiers `package.json` et `composer.json`, la documentation et les messages de commit, les commandes utilisent les **noms longs** de leurs options, plus lisibles :

| **Forme courte** | **Forme attendue** |
| --- | --- |
| `git switch -c` | `git switch --create` |
| `git push -u` | `git push --set-upstream` |
| `git commit -m` | `git commit --message` |
| `npm install -D` | `npm install --save-dev` |
| `composer install -n` | `composer install --no-interaction` |
| `bash -lc` | `bash --login -c` |

Une option qui n'a pas de nom long garde sa forme courte.
