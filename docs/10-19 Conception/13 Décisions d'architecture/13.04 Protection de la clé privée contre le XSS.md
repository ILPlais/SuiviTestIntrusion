# 13.04 Protection de la clé privée contre le XSS

## Contexte

La clé privée OpenPGP de l'utilisateur est déchiffrée dans le navigateur ([[13.01 Format de chiffrement des preuves]], [[13.02 Dérivation de clé Argon2id]]), et le mot de passe qui la protège y est saisi ([[13.03 Authentification locale et coffre de clés]]). Le [[12.01 Rapport d'analyse du CDC]] (§4.4) relève qu'un XSS réussi compromet aussitôt cette clé. Il demande une CSP stricte (§4.4 et §3.2), dont 13.01 conclut aussi qu'elle reste indispensable.

Le risque est plus fort ici qu'ailleurs : les données d'un test d'intrusion contiennent couramment des charges XSS. Descriptions de vulnérabilités, sorties d'outils, journaux, libellés du diagramme réseau, noms et contenus des preuves : tout contenu saisi ou importé est hostile par nature.

Contraintes :

- la SPA est un build Vite statique servi par le service `web` ([[11.02 Socle technique]]) ; `index.html` n'est pas généré par Laravel ;
- argon2id et le S2K d'openpgp.js compilent du WebAssembly ;
- le CDC prévoit Mermaid pour le diagramme réseau ([[11.07 Périmètre]]), PrismJS pour les sorties d'outils et asciinema-player pour les enregistrements de terminal ([[11.08 Déroulement du test]]) ;
- Swagger UI est servie par la même origine, pour les administrateurs ([[11.03 Serveur et API REST]]) ;
- le serveur ne doit jamais pouvoir lire une preuve.

## Options

Pour la CSP :

1. **Liste blanche `'self'`**, en-tête statique posé par le serveur web : simple, compatible avec un `index.html` statique. Elle suppose que l'origine ne serve aucun contenu interprétable comme script.
2. **Nonce et `'strict-dynamic'`** : utile quand une page contient des scripts inline. Elle impose de générer `index.html` à chaque requête, alors que le build n'en contient aucun.

Pour la place de la clé déchiffrée :

1. **Fil principal** : le plus simple ; un XSS qui franchit la CSP lit la clé.
2. **Web Worker dédié** : la clé et les CEK restent dans le Worker, le fil principal ne reçoit que des résultats. Un XSS peut encore se servir du Worker pendant la session, mais ne peut pas emporter la clé.
3. **Iframe sur une autre origine** : isolation la plus forte, mais un second nom de domaine et une SPA plus complexe.

## Décision

**CSP par liste blanche `'self'` avec Trusted Types**, et **clé privée confinée dans un Web Worker dédié**.

### CSP de la SPA

Le serveur web la pose sur **toutes** les réponses de la SPA (document, scripts, WASM) : la CSP d'un Worker est celle de la réponse qui sert son script.

| **Directive** | **Valeur** | **Raison** |
| --- | --- | --- |
| `default-src` | `'none'` | Tout est interdit, sauf ce qui suit |
| `script-src` | `'self' 'wasm-unsafe-eval'` | Scripts du build uniquement ; compilation WASM d'argon2id, d'openpgp.js et du terminal d'asciinema-player. Ni `'unsafe-inline'`, ni `'unsafe-eval'` |
| `style-src` | `'self' 'unsafe-inline'` | Mermaid insère un élément `<style>`, et d3 des attributs `style` |
| `img-src` | `'self' blob:` | Aperçus des preuves déchiffrées |
| `font-src`, `connect-src`, `worker-src`, `manifest-src` | `'self'` | Aucun échange avec un tiers : pas d'exfiltration par `fetch`, image, police ou feuille de style |
| `object-src`, `frame-src` | `'none'` | Aucun plugin, aucun cadre |
| `base-uri` | `'none'` | Pas de détournement des URL relatives |
| `form-action` | `'self'` | Formulaires vers l'application seulement |
| `frame-ancestors` | `'none'` | Pas d'intégration dans un cadre (clickjacking) |
| `require-trusted-types-for` | `'script'` | Aucune chaîne brute dans `innerHTML`, `script.src`, `new Worker`… |
| `trusted-types` | `sti-render sti-worker dompurify default` | Politiques autorisées, détaillées ci-dessous ; `vue` refusée |
| `report-uri`, `report-to` | `/api/v1/csp-reports`, `csp` | Rapports de violation |

En-têtes associés : `Reporting-Endpoints: csp="https://<instance>/api/v1/csp-reports"` et `X-Content-Type-Options: nosniff`.

`'unsafe-inline'` ne vaut que pour les styles. Un style injecté n'exécute pas de code. Pour exfiltrer une donnée, il devrait charger une ressource tierce, ce que `img-src`, `font-src` et `connect-src` interdisent.

### Politiques Trusted Types

| **Politique** | **Rôle** |
| --- | --- |
| `sti-render` | Module de rendu unique : assainit le HTML avec DOMPurify avant insertion (PrismJS, SVG Mermaid) |
| `sti-worker` | Pour `new Worker`, n'accepte que l'URL du Worker crypto (`/assets/crypto.worker-*.js`, même origine) |
| `dompurify` | Créée par DOMPurify ; une seule copie de DOMPurify dans le build, partagée avec Mermaid |
| `default` | Filet pour les bibliothèques qui écrivent du HTML brut (Mermaid, gabarits d'asciinema-player) : assainit avec DOMPurify, refuse tout script et toute URL de script |

Vue crée une politique `vue` qui laisse tout passer et sert à `v-html` : elle est **refusée**. Vue l'utilise aussi pour insérer le contenu statique sérialisé par le compilateur ; le build désactive donc cette sérialisation (`hoistStatic: false`). Le refus produit à chaque chargement une violation attendue, que le point de réception ignore.

### En-têtes de l'API

- Toutes les réponses de `/api/` portent `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; sandbox` et `X-Content-Type-Options: nosniff`.
- Le JSON est servi en `application/json`, les blobs en `application/octet-stream` avec `Content-Disposition: attachment`.
- Aucun JSONP.

Ces en-têtes rendent sûre la liste blanche `'self'` : une réponse de l'API, même chargée par une balise `<script>`, n'est jamais exécutée.

**Swagger UI** reçoit sa propre CSP, avec un nonce posé par Laravel. La page reste réservée aux administrateurs et désactivable.

**Point de réception** `/api/v1/csp-reports` : public, car les navigateurs envoient les rapports sans cookie. Il est limité en débit et en taille, accepte `application/csp-report` et `application/reports+json`, et consigne les violations dans le journal technique.

### Worker crypto

Un Worker module unique charge openpgp.js et argon2id ; le fil principal n'importe aucune des deux bibliothèques. Le Worker est créé à partir de l'URL émise par Vite (`?worker&url`), via la politique `sti-worker`.

| **Message** | **Effet** |
| --- | --- |
| `auth` | Calcule la valeur d'authentification ([[13.03 Authentification locale et coffre de clés]]) |
| `enroll`, `unlock` | Génère la paire et ses copies chiffrées ; déverrouille la clé (S2K) |
| `encryptFile`, `decryptFile` | Chiffre ou déchiffre un fichier ([[13.01 Format de chiffrement des preuves]]) |
| `share` | Chiffre une CEK pour un nouveau destinataire |
| `rotate`, `recover` | Changement de mot de passe et récupération ([[13.02 Dérivation de clé Argon2id]], 13.03) |

- Ne sortent **jamais** du Worker : la clé privée déchiffrée, les CEK et le mot de passe une fois utilisé.
- En sortent : `auth`, les copies chiffrées de la clé, les paquets chiffrés, l'empreinte et le clair des fichiers à afficher.
- Le Worker refuse toute opération hors de cette liste.
- **Verrouiller** revient à arrêter le Worker (`terminate()`). Un nouveau Worker reste verrouillé tant que l'utilisateur n'a pas ressaisi son mot de passe. Les délais relèvent du §4.3 de 12.01 (story `ged-chiffree-2`).

### Rendu des contenus hostiles

- Texte : interpolation Vue (`{{ }}`) ou `textContent` uniquement.
- `v-html` est interdit. `innerHTML` et ses équivalents ne s'écrivent que dans le module de rendu, via `sti-render`.
- ESLint bloque en CI : `vue/no-v-html`, `no-eval`, `no-implied-eval`, `no-new-func`, et les écritures dans `innerHTML`, `outerHTML`, `insertAdjacentHTML` et `document.write` hors du module de rendu.
- PrismJS : mode manuel, `Prism.highlight` sur le texte brut (les jetons sont échappés), résultat inséré via `sti-render`.
- Mermaid : `securityLevel: 'strict'` ; le SVG est inséré via `sti-render`.
- asciinema-player : l'enregistrement déchiffré lui est passé en mémoire (`{ data }`), jamais par une URL ; `keystrokeOverlay` reste désactivé, pour ne pas afficher les frappes enregistrées. Ses gabarits passent par la politique `default` ; le contenu du terminal s'affiche comme du texte.
- vue-i18n : messages sans HTML ; les paramètres s'affichent comme du texte.
- Build : `template.compilerOptions.hoistStatic: false` ; `build.assetsInlineLimit: 0`, car aucune ressource ne doit devenir une URL `data:` (le WASM de secours d'argon2id serait bloqué par `connect-src`).

### Aperçus des preuves déchiffrées

- Seuls s'affichent dans l'application les images PNG, JPEG, WebP et GIF (`<img>` sur une URL `blob:`) et le texte (`textContent`, taille limitée).
- Les enregistrements asciinema (`.cast`) se rejouent dans asciinema-player ([[11.08 Déroulement du test]], Outils).
- SVG, HTML, XML, PDF et tout autre type : téléchargement seul, avec un blob typé `application/octet-stream`.
- Une URL `blob:` de contenu déchiffré ne s'ouvre jamais dans un onglet ou un cadre : le document hériterait de l'origine de l'application.

### Dépendances et export HTML

- Tout le code est servi par l'origine, sans CDN ; versions épinglées, lockfile, `npm audit` en CI.
- Le rapport HTML exporté ([[11.04 Exports et modèles de rapport]]) échappe tout contenu saisi et porte une CSP en `<meta>` qui interdit tout script.

### Limites résiduelles

- Un XSS qui franchirait ces barrières pourrait, pendant la session, demander au Worker de déchiffrer les fichiers accessibles ; il ne pourrait pas emporter la clé.
- Il pourrait exfiltrer des données par navigation (`location`, `window.open`), que la CSP ne couvre pas.
- Le mot de passe est saisi dans le fil principal : un XSS actif au moment de la connexion pourrait le capturer.
- Ces mesures ne protègent ni contre une extension malveillante, ni contre un poste compromis, ni contre un serveur compromis qui servirait un code modifié : le serveur distribue le code, comme il distribue les clés publiques ([[11.11 Documents et chiffrement]], Points de vigilance).
- La politique `default` assainit au lieu de bloquer : un `v-html` oublié serait assaini, pas refusé. L'interdiction par ESLint reste la règle.
- Trusted Types n'a été vérifié qu'avec Firefox 159 et Chrome 157. Là où il manque, la CSP et DOMPurify restent les barrières.

### Preuve de faisabilité

Validée le 2026-11-11 avec une mini SPA : Vite 8.3.5, Vue 3.5.44, Pinia 4.1.0, vue-i18n 11.4.16, openpgp 6.1.1, argon2id 1.0.1, Mermaid 12.2.0, PrismJS 1.30.0 et DOMPurify 3.4.17. Elle était servie par un serveur Node avec la CSP ci-dessus et pilotée par puppeteer-core 25.16.0, dans Firefox 159.0.1 et Chrome for Testing 157.0.8103.50, tous deux sans interface.

Avec la CSP retenue, dans les deux navigateurs :

- tout fonctionne : montage Vue (contenu statique compris), vue-i18n et Pinia ; dans le Worker, calcul de `auth`, génération et déverrouillage d'une clé v6, chiffrement et déchiffrement de 1 Mio à l'identique ; aperçu PNG via `blob:` ; PrismJS ; diagramme Mermaid avec ses styles ;
- les seules violations relevées sont attendues : le refus de la politique `vue` et, sous Chrome, le gestionnaire `onerror` de la charge du libellé Mermaid, bloqué par `script-src-attr` ;
- les charges XSS d'une sortie d'outil, d'un libellé Mermaid, d'un paramètre i18n et d'une interpolation s'affichent comme du texte ;
- sont bloqués : `<img onerror>` et `<script>` injectés, script externe, script de même origine servi par l'API en `octet-stream`, `eval`, `new Function`, `fetch` et image vers une autre origine ;
- le Worker refuse une opération inconnue (`exportKey`) ; aucun objet clé n'est accessible depuis le fil principal ; openpgp.js n'est présent que dans le chunk du Worker ;
- après `terminate()`, toute demande au Worker échoue, et un nouveau Worker refuse de déchiffrer.

Variantes de contrôle :

| **Variante** | **Constat** |
| --- | --- |
| Sans `'wasm-unsafe-eval'` | Calcul de `auth` et génération de clé bloqués dans le Worker |
| `style-src 'self'` seul | Diagramme Mermaid sans style (nœuds noirs), dizaines de violations `style-src` |
| Sans politique `default` | Mermaid échoue : il écrit du HTML brut |
| Worker créé avec une URL brute | Refusé par Trusted Types ; d'où la politique `sti-worker` |
| Politique `vue` autorisée | `v-html` franchit Trusted Types ; seul `script-src` bloque encore l'`onerror` |
| Politique `vue` refusée, build Vue par défaut | L'application ne s'affiche plus : le contenu statique passe par `innerHTML` |
| Sans Trusted Types | Les attaques restent bloquées par la CSP seule ; `v-html` insère le HTML |
| Build sans `assetsInlineLimit: 0` | Le WASM sans SIMD d'argon2id devient une URL `data:` |

Rapports : Firefox a transmis les rapports `report-to` au serveur en moins de 2 s. Chrome sans interface n'en a transmis aucun en 70 s, en HTTP local ; à revérifier en HTTPS (story `socle-6`).

#### Complément du 2026-11-11 : asciinema-player

Le rejeu des enregistrements de terminal ([[11.08 Déroulement du test]], Outils) a été vérifié avec la même mini SPA, augmentée d'asciinema-player 3.17.0, dans les mêmes navigateurs. Deux enregistrements, asciicast v2 et v3, contenaient une charge `<img onerror>` et `<script>`, un hyperlien OSC 8 vers `javascript:`, un OSC 52, deux marqueurs, un événement d'entrée et des caractères de cadre. Ils étaient passés au lecteur en mémoire.

Avec la CSP retenue, dans les deux navigateurs :

- lecture complète, pause et saut au marqueur suivant fonctionnent ; couleurs et caractères de cadre s'affichent ;
- aucune violation, aucune requête hors de l'origine ; le WASM du terminal est intégré au script, sans URL `data:` ;
- les charges s'affichent comme du texte ; aucun lien n'est créé, ni l'entrée enregistrée ni l'OSC 52 ne s'affichent ;
- la transcription texte (sorties sans séquences de contrôle) est exacte et exclut l'entrée.

| **Variante** | **Constat** |
| --- | --- |
| Sans politique `default` | Le lecteur ne se crée pas : ses gabarits SolidJS passent par `innerHTML` |
| `style-src 'self'` seul | Le lecteur fonctionne : il n'a pas besoin de `'unsafe-inline'` |
| Sans `'wasm-unsafe-eval'` | Le terminal ne s'initialise pas ; rien ne s'affiche |

## Conséquences

- **CDC** : [[11.11 Documents et chiffrement]] reçoit une section *Protection contre le XSS*. [[11.03 Serveur et API REST]] précise les en-têtes de l'API et la CSP de Swagger UI, et [[11.04 Exports et modèles de rapport]] encadre le rapport HTML.
- **Exploitation** : le service `web` (configuration Docker) pose la CSP et les en-têtes sur toutes les réponses ; l'installation manuelle reprend la même configuration, documentée.
- **Front-end** : Worker crypto unique, module de rendu unique, politiques Trusted Types, options de build (`hoistStatic: false`, `assetsInlineLimit: 0`) et règles ESLint.
- **Back-end** : en-têtes de l'API, point de réception des rapports, CSP propre à Swagger UI.
- **Tests** : tests E2E Playwright sur la CSP (aucune violation inattendue, charges XSS affichées comme texte), sous Firefox et Chromium.
- **Stories** : `socle-3` (ESLint), `socle-6` (CSP et en-têtes), `identite-1`, `ged-chiffree-1`, `ged-chiffree-2`, `ged-chiffree-4`, `deroulement-6`, `deroulement-8`, `engagement-6` et `exports-2` appliquent cet ADR. `decisions-4` garde CORS, TLS/HSTS et les cookies.
- **Évolution** : isoler Mermaid dans une iframe `sandbox` permettrait de retirer `'unsafe-inline'`. Retirer aussi la politique `default` exigerait d'isoler asciinema-player de la même façon. À réévaluer si Mermaid et asciinema-player deviennent compatibles avec Trusted Types.
