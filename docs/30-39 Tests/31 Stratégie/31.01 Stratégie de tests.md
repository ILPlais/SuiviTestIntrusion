# 31.01 Stratégie de tests

## Niveaux de tests

| **Niveau**        | **Outil**                                       | **Emplacement**                  | **Commande**                         |
| ----------------- | ----------------------------------------------- | -------------------------------- | ------------------------------------ |
| Unitaires serveur | PHPUnit                                         | `backend/tests/Unit/`            | `php artisan test` (dans `backend/`) |
| Fonctionnels API  | PHPUnit, sur SQLite, MySQL, MariaDB, PostgreSQL | `backend/tests/Feature/`         | `php artisan test`                   |
| Unitaires client  | Vitest (jsdom)                                  | `frontend/tests/unit/`           | `npm test` (dans `frontend/`)        |
| Bout en bout      | Playwright (Chromium) et axe                    | `frontend/tests/e2e/`            | `npm run test:e2e`                   |
| Licences          | `node --test`                                   | `scripts/licenses/`              | `node scripts/licenses/licenses.mjs` |
| Sécurité          | Analyse statique, audit                         | CI (`socle-3`, `exploitation-5`) | voir *Qualité du code*               |

Outils confirmés par la story `socle-3` : Pest n'est pas retenu, PHPUnit suffit. Les tests de bout en bout démarrent l'API Laravel et la SPA, puis vérifient le parcours et l'absence de violation d'accessibilité détectable (WCAG 2.2 A et AA, [[13.07 Licence, langues et accessibilité]]). En local, Chromium demande ses bibliothèques système (une fois : `sudo npx playwright install-deps chromium` dans WSL).

## Qualité du code

| **Contrôle**         | **Outil**                                                              | **Commande**                                      |
| -------------------- | ---------------------------------------------------------------------- | ------------------------------------------------- |
| Style PHP            | PHP-CS-Fixer (PSR-12 en tabulations, 21.01)                            | `composer lint`, correction : `composer lint:fix` |
| Analyse statique     | Larastan niveau 6 ; vue-tsc pour la SPA                                | `composer analyse`, `npm run typecheck`           |
| Style et sécurité JS | ESLint : règles de 13.04, textes en dur interdits (13.07), tabulations | `npm run lint`, correction : `npm run lint:fix`   |

## Intégration continue

Le workflow `.github/workflows/ci.yml` s'exécute à chaque poussée sur `main`, `feature/**` et `fix/**` : API sur les quatre bases (PHP 8.3, version minimale du CDC), SPA (lint, types, tests, build), bout en bout, licences. Une branche n'est fusionnée dans `main` que si la CI est verte ; son état se lit avec `gh run list --branch feature/<id>`.

## Campagnes de tests

Une campagne regroupe les tests manuels et les vérifications faites avant une publication.

- Un compte rendu par campagne : `32.xx Campagne vX.Y.Z.md`, référencé dans [[32.00 Index des campagnes]].
- Partir du modèle [[01.04 Modèle campagne de tests]].
- Chaque anomalie trouvée devient une fiche de bug `52.xx` (voir [[51.01 Traitement des retours]]).
